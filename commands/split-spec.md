# split-spec

## 目的

大規模な仕様書を処理する際のコンテキスト肥大化を防ぐため、仕様書から機能を抽出し、機能単位（F-001, F-002等）でタスクに分割します。生成されたタスクファイルにより、`/origami:run-task` で順次実行できます。

**機能別ディレクトリ方式**: 各機能を独立したディレクトリ（`F-XXX_{機能名}/`）に出力することで、後続タスク実行時のコンテキスト肥大化を防止します。各タスクは自機能フォルダのみを参照し、他の機能のファイルは参照しません。

## 事前準備

1. **追加ルールの読み込み**
   - `docs/rule` ディレクトリが存在する場合は読み込み
   - `docs/rule/origami` ディレクトリが存在する場合は読み込み
   - 各ディレクトリ内のすべてのファイルを読み込み、追加ルールとして適用

2. **出力先ディレクトリの決定** 🔵
   - 入力ファイル名から出力先ディレクトリを自動決定
   - ディレクトリ名は入力ファイル名から拡張子を除いたものを使用
   - 出力先: `docs/origami/{仕様書名}/`
   - 例: `ecommerce-spec.md` → `docs/origami/ecommerce-spec/`

3. **既存出力の確認** 🔵
   - 出力先ディレクトリ `docs/origami/{仕様書名}/` が既に存在するか確認
   - **存在する場合**: AskUserQuestionツールで確認プロンプトを表示
     - 「上書きする」: 既存ディレクトリを削除して新規作成
     - 「中断する」: 処理を中断
   - **存在しない場合**: 新規ディレクトリを作成して続行

## 入力

以下の形式を受け付けます：

| 形式 | 説明 | 例 |
|------|------|-----|
| Markdown | .md拡張子のファイル | `/origami:split-spec docs/requirements.md` |
| テキスト | .txt拡張子のファイル | `/origami:split-spec spec.txt` |
| URL | Web上のページ | `/origami:split-spec https://example.com/api-spec` |

### 出力先の決定ルール

| 入力形式 | 仕様書名の決定方法 | 出力先 |
|---------|-------------------|--------|
| Markdownファイル | 拡張子を除いたファイル名 | `docs/origami/{ファイル名}/` |
| テキストファイル | 拡張子を除いたファイル名 | `docs/origami/{ファイル名}/` |
| URL | ドメイン+パスをケバブケース化 | `docs/origami/{domain-path}/` |

**URL入力の例**:
- `https://example.com/api/docs` → `docs/origami/example-com-api-docs/`
- `https://shop.example.org/spec` → `docs/origami/shop-example-org-spec/`

## 実行内容

**【信頼性レベル指示】**:
各項目について、入力仕様書との照合状況を以下の信号でコメントしてください：

- 🟢 **青信号**: 入力仕様書に明示的な記載がある
- 🟡 **黄信号**: テスト技法・業界標準・Web常識から推測
- 🔴 **赤信号**: 推測の根拠が薄い

### 1. 入力解析

- 指定されたファイルまたはURLの内容を取得
- **入力ファイル名から出力先ディレクトリ名を決定** 🔵
- 入力形式が不正な場合はエラーメッセージを表示

### 2. 出力先ディレクトリの確認と作成 🔵

- 出力先ディレクトリ `docs/origami/{仕様書名}/` の存在を確認
- **既存ディレクトリがある場合**:
  ```
  AskUserQuestion({
    questions: [{
      question: "出力先ディレクトリ 'docs/origami/{仕様書名}/' が既に存在します。既存の出力を削除して再生成しますか？",
      header: "上書き確認",
      multiSelect: false,
      options: [
        {
          label: "上書きする",
          description: "既存ディレクトリを削除して新しく生成"
        },
        {
          label: "中断する",
          description: "処理を中断してコマンドを終了"
        }
      ]
    }]
  })
  ```
- 「上書きする」選択時: 既存ディレクトリを削除
- 「中断する」選択時: 「処理を中断しました」と表示して終了
- ディレクトリ構造を作成:
  - `docs/origami/{仕様書名}/`
  - `docs/origami/{仕様書名}/tasks/`

### 3. 機能抽出

- 既存の `docs/origami/{仕様書名}/01_機能一覧.md` がある場合は優先的に使用
- 「〜できる」「〜する」等の動詞を含む記述を機能として抽出
- 具体的なエンドポイント・画面名の記載を機能として抽出
- URL入力の場合、画面要素から機能を推測
- 各機能に F-XXX 形式のIDを付与（F-001, F-002, ...）
- **機能論理名の抽出** 🔵: 各機能について日本語の論理名を抽出（例: 「ログイン」「ユーザー登録」）
- **出力先ディレクトリパスの生成** 🔵: `F-{連番}_{機能論理名}/` 形式でパスを生成
  - 連番: 3桁ゼロ埋め（001, 002, 003, ...）
  - 機能論理名: スペースはアンダースコアに置換
  - 例: `F-001_ログイン/`, `F-002_ユーザー登録/`

### 4. 依存関係分析

- 機能間の依存関係を特定
- 例：ログイン機能は登録機能に依存しない、プロフィール編集はログインに依存
- 依存関係がある場合はタスクに記載

### 5. タスク生成

- 各機能に TASK-XXX 形式のIDを付与
- タスク番号は入力順に連番で付与（TASK-001, TASK-002, ...）
- 各タスクに処理対象の機能を紐付け
- 依存タスクがある場合は明記
- **各タスクに以下の情報を付与** 🔵:
  - 機能ID（F-XXX形式）
  - 機能名（日本語論理名）
  - 出力先ディレクトリパス（`docs/origami/{仕様書名}/F-XXX_{機能名}/`）

### 6. タスクファイル出力 🔵

- `docs/origami/{仕様書名}/tasks/task-list.md` にタスク一覧を出力
- **概要セクションに「出力先:」フィールドを追加**
- チェックボックス形式で進捗管理可能な形式

## 信号機判定基準

| 信号 | 判定条件 | 例 |
|------|---------|-----|
| 🟢 青信号 | 入力に「〜できる」「〜する」等の明示的記述がある | 「ユーザーは新規登録できる」 |
| 🟢 青信号 | 具体的なエンドポイント・画面名の記載がある | 「POST /api/users」 |
| 🟡 黄信号 | 記載された機能から一般的に必要と類推される | ログインがあればログアウトも必要 |
| 🔴 赤信号 | 「検討中」「予定」等の不明確な表現がある | 「将来的に実装予定」 |
| 🔴 赤信号 | URL解析で推測の根拠が薄い | 画面要素のみから推測 |

出力先: `docs/origami/{仕様書名}/tasks/task-list.md`

## エラーハンドリング

| エラーケース | 対応 |
|------------|------|
| 入力ファイルが見つからない | エラー: 「ファイルが見つかりません: {パス}」を表示 |

| 機能が抽出できない | 警告: 「機能が見つかりませんでした。入力内容を確認してください」を表示 |
| 出力先ディレクトリ作成失敗 | エラー: 「ディレクトリを作成できません: {パス}」を表示 |

## 実行後の確認

- `docs/origami/{仕様書名}/tasks/task-list.md` が作成されたことを確認
- 出力先ディレクトリ構造が正しく作成されたことを確認:
  ```
  docs/origami/{仕様書名}/
  └── tasks/
      └── task-list.md
  ```
- task-list.md の各タスクに以下のフィールドが含まれることを確認:
  - 機能ID（F-XXX形式）
  - 機能名（日本語論理名）
  - 出力先（`docs/origami/{仕様書名}/F-XXX_{機能名}/` 形式）
- 生成されたタスク数を表示
- 信号別の件数サマリーを表示
- 次のステップ（run-task）を案内
  - 各タスクの出力先ディレクトリパスを案内に含める

## 関連コマンド

| コマンド | 説明 |
|---------|------|
| `/origami:run-task` | 生成されたタスクを個別に実行（task-list.mdの出力先に機能ディレクトリを作成） |
| `/origami:verify-tasks` | 機能ディレクトリ構造を確認し、タスク完了状況を集計 |
| `/origami:extract-features` | 機能一覧を抽出（split-spec内で呼び出される） |

## 機能別ディレクトリ方式について

### 新しいディレクトリ構造

run-task実行後の最終的なディレクトリ構造:

```text
docs/origami/{仕様書名}/
├── F-001_ログイン/
│   ├── 01_機能詳細.md
│   ├── 02_動作仕様.md
│   ├── 03_境界値分析.md
│   └── 04_テストケース.md
├── F-002_ユーザー登録/
│   ├── 01_機能詳細.md
│   ├── 02_動作仕様.md
│   ├── 03_境界値分析.md
│   └── 04_テストケース.md
├── F-003_商品検索/
│   └── ...
└── tasks/
    └── task-list.md
```

### メリット

1. **コンテキスト一定**: 各タスク実行時、自機能フォルダのみ参照
2. **独立性**: 機能単位で完結、並列レビュー可能
3. **再実行容易**: 特定機能だけ再生成可能
4. **可読性向上**: 機能論理名でディレクトリ内容が明確

### Breaking Change（v3.0.0）

- 既存の追記方式（`01_機能一覧.md` など）との互換性はありません
- 単独実行時のデフォルト動作は変更なし（後方互換）
