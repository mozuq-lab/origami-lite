# generate-checklist

## 目的

機能一覧または仕様書から、各機能の「できなければならないこと（Must）」と「できてはいけないこと（Never）」を整理し、テスト観点の抜け漏れを防ぎます。
信号機システム（🟢🟡🔴）により、各項目の確信度を可視化し、レビュー優先度を明確にします。

**実行コンテキストに応じたファイル出力**:
- **単独実行時**: 複数機能を一覧形式で `02_動作仕様一覧.md` に出力（後方互換）
- **タスク分割経由時**（`--target` 指定）: 単一機能の仕様を `02_動作仕様.md` に出力

## 事前準備

1. **出力先ディレクトリの決定** 🔵
   - `--output` 引数が指定されている場合はそのディレクトリを使用
   - 指定がない場合は入力ファイル名から出力先を自動決定:
     - 入力ファイル名から拡張子を除去してディレクトリ名を生成
     - 出力先: `docs/origami/{仕様書名}/`
     - 例: `ecommerce-spec.md` → `docs/origami/ecommerce-spec/`

2. **前工程出力の確認**
   - `{出力先}/01_機能一覧.md` が存在する場合は読み込み
   - 存在しない場合は、入力として指定された仕様書から直接処理

3. **追加ルールの読み込み**
   - `docs/rule` ディレクトリが存在する場合は読み込み
   - `docs/rule/origami` ディレクトリが存在する場合は読み込み
   - 各ディレクトリ内のすべてのファイルを読み込み、追加ルールとして適用

4. **出力ディレクトリの作成**
   - 出力ディレクトリが存在しない場合は作成

## 入力

### 引数 🔵

| 引数 | 説明 | 必須 | 例 |
|------|------|------|-----|
| 仕様書 | 入力ファイルまたはURL | △ | `docs/requirements.md` |
| --output | 出力先ディレクトリ（機能ディレクトリを含む） | △ | `--output docs/origami/my-spec/F-001_ログイン/` |
| --target | 対象機能ID（タスク分割経由時） | △ | `--target F-001` |

**引数の組み合わせによる動作**:

| --target | --output | 出力ファイル名 | 用途 |
|----------|----------|---------------|------|
| なし | なし | `02_動作仕様一覧.md` | 単独実行（全機能処理） |
| なし | あり | `02_動作仕様一覧.md` | 単独実行（出力先指定） |
| あり | あり | `02_動作仕様.md` | タスク分割経由（単一機能） |

### 入力優先度

| 優先度 | 入力 | 説明 |
|--------|------|------|
| 1 | {出力先}/01_機能一覧.md | 前工程の出力（推奨） |
| 2 | 仕様書（.md/.txt） | 単独実行時の直接入力 |
| 3 | URL | Web上のページ |

### タスク分割経由時の入力制限 🔵

`--target` オプション指定時は、以下のルールに従います：

- **入力**: `{出力先ディレクトリ}/01_機能詳細.md` のみ
- **重要**: 他の機能フォルダ（F-001_xxx/, F-002_xxx/ 等）のファイルは参照しない
- これにより、コンテキストサイズが一定に保たれます

```text
入力制限ルール:

タスク分割経由時（--target F-001 指定）
  ✅ 参照可能: {機能ディレクトリ}/01_機能詳細.md
  ❌ 参照禁止: 他の機能フォルダのファイル
  ❌ 参照禁止: 仕様書全体
```

### フェーズ間入力制限（v3.1.0） 🔵

**Phase 2（generate-checklist）の入力制限**:

| 実行モード | 入力 | 備考 |
|-----------|------|------|
| タスク分割経由時 | `{機能ディレクトリ}/01_機能詳細.md` **のみ** | 仕様書・他機能フォルダは参照禁止 |
| 単独実行時 | 仕様書または機能一覧 | 後方互換 |

**コンテキスト分離のポイント**:
- Phase 2は `01_機能詳細.md` **のみ**を参照（仕様書は参照しない）
- これにより、Phase 1の出力品質が直接影響
- 🔴項目がある場合は、Phase 2実行前に修正推奨

### 事前チェック（タスク分割経由時） 🟡

タスク分割経由時（`--target` 指定時）は、以下の事前チェックを行います：

1. `{機能ディレクトリ}/01_機能詳細.md` の存在を確認
2. 存在しない場合はエラー:
   ```
   エラー: 入力ファイルが見つかりません: {パス}/01_機能詳細.md

   先に Phase 1 を実行してください:
   /origami:run-task {タスクID} --phase 1
   ```

### 使用例 🔵

```bash
# 単独実行（出力先自動決定）
/origami:generate-checklist docs/ecommerce-spec.md
# → docs/origami/ecommerce-spec/02_動作仕様一覧.md に出力

# 出力先を明示的に指定
/origami:generate-checklist --output docs/origami/my-project/
# → docs/origami/my-project/01_機能一覧.md を読み込み、02_動作仕様一覧.md に出力

# タスク分割経由（run-taskから呼び出し）
/origami:generate-checklist --output docs/origami/ecommerce-spec/F-001_ログイン/ --target F-001
# → F-001_ログイン/01_機能詳細.md を読み込み、02_動作仕様.md に出力
```

## 実行内容

1. **入力の読み込み**
   - 機能一覧または仕様書を読み込み
   - 機能ごとに処理を実行

2. **Must項目の抽出**
   以下のパターンをMust項目として抽出する：
   - 「〜できる」という記述 → 「〜できなければならない」に変換
   - 「〜する」「〜を行う」という記述 → 「〜しなければならない」に変換
   - 正常系フローの記述 → Must項目として整理
   - ユーザー体験要件 → Must項目として整理

3. **Never項目の抽出**
   以下のパターンをNever項目として抽出する：
   - 「〜できない」「〜禁止」という記述 → Never項目として抽出
   - 「〜してはいけない」「〜不可」という記述 → Never項目として抽出
   - セキュリティ観点（OWASP Top 10等）から🟡としてNever項目を追加
   - データ整合性観点から🟡としてNever項目を追加

4. **セキュリティ観点の追加（🟡項目）**
   以下の観点でNever項目を追加する：
   - **認証・認可**: 未認証アクセス禁止、権限外操作禁止
   - **入力検証**: SQLインジェクション、XSS、パストラバーサル対策
   - **データ保護**: 機密情報の平文保存禁止、適切な暗号化
   - **セッション管理**: セッションハイジャック対策
   - **エラー処理**: 詳細なエラー情報の露出禁止

5. **信号機判定**
   - 各項目に信号（🟢🟡🔴）を付与
   - 🟡項目は判断詳細を記録

6. **サマリー生成**
   - 機能別・信号別の件数を集計

7. **出力ファイル名の決定** 🔵

   実行コンテキストに応じて出力ファイル名を切り替え：

   ```text
   IF --target オプションが指定されている THEN
     出力ファイル名 = "02_動作仕様.md"
   ELSE
     出力ファイル名 = "02_動作仕様一覧.md"
   END IF
   ```

   | 条件 | 出力ファイル名 | 出力形式 |
   |------|---------------|---------|
   | 単独実行（--targetなし） | `02_動作仕様一覧.md` | 複数機能を一覧形式で記載 |
   | タスク分割経由（--targetあり） | `02_動作仕様.md` | 単一機能の仕様を記載 |

## 信号機判定基準

| 信号 | 判定条件 | 例 |
|------|---------|-----|
| 🟢 青信号 | 仕様書に明示的な記述がある | 「重複メールアドレスは登録できない」 |
| 🟢 青信号 | 機能一覧に明記されている | 「ログイン機能」→ログインできなければならない |
| 🟡 黄信号 | テスト技法から導出される | 境界値でのエラー処理 |
| 🟡 黄信号 | OWASP Top 10等の業界標準に基づく | SQLインジェクション対策 |
| 🟡 黄信号 | Webアプリケーション一般の常識 | 入力バリデーション |
| 🔴 赤信号 | 仕様書に記載がなく、推測の根拠も薄い | アクセス制御の詳細 |
| 🔴 赤信号 | 業務ドメイン固有で確認が必要 | 業務ルールに基づく制約 |

## セキュリティ観点チェックリスト（参考）

### OWASP Top 10 (2021) に基づく観点

1. **A01: アクセス制御の不備**
   - 認証なしでの機密情報アクセス禁止
   - 権限昇格の防止

2. **A02: 暗号化の失敗**
   - 平文での機密データ保存禁止
   - 弱い暗号アルゴリズムの使用禁止

3. **A03: インジェクション**
   - SQLインジェクション対策
   - コマンドインジェクション対策
   - XSS対策

4. **A04: 安全でない設計**
   - ビジネスロジックの不正利用防止

5. **A05: セキュリティ設定ミス**
   - デフォルト認証情報の使用禁止
   - 不要な機能の無効化

6. **A06: 脆弱で古いコンポーネント**
   - 既知の脆弱性を持つライブラリ使用禁止

7. **A07: 識別と認証の失敗**
   - ブルートフォース攻撃対策
   - セッション管理の適切な実装

8. **A08: ソフトウェアとデータの整合性の障害**
   - 安全でないデシリアライゼーション対策

9. **A09: セキュリティログと監視の失敗**
   - 重要操作のログ記録

10. **A10: SSRF（サーバーサイドリクエストフォージェリ）**
    - 外部URLの検証

## コンテキスト分離（v3.1.0） 🔵

Phase 2（generate-checklist）は、Phase 1の出力のみを入力として受け取ります。

| フェーズ | コマンド | 入力 | 出力 |
|---------|---------|------|------|
| Phase 1 | extract-features | 仕様書（対象機能部分） | `01_機能詳細.md` |
| **Phase 2** | generate-checklist | `01_機能詳細.md` **のみ** | `02_動作仕様.md` |
| Phase 3 | analyze-boundaries | `02_動作仕様.md` のみ | `03_境界値分析.md` |
| Phase 4 | generate-cases | `01` + `02` + `03` | `04_テストケース.md` |

**重要**: Phase 2 は仕様書を直接参照しません。Phase 1 で抽出された情報のみを基に動作仕様を生成します。これにより:
- コンテキストサイズが一定に保たれる
- 各フェーズの処理が独立して実行可能
- 中間成果物のレビュー・修正が容易

## v3.1.0 Breaking Change

- **タスク分割経由時の入力制限**: `01_機能詳細.md` のみを入力（仕様書参照禁止）
- **コンテキスト分離**: 前フェーズ出力のみを参照
- **事前チェック**: 入力ファイル存在確認を追加
