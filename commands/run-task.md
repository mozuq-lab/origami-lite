# run-task

## 目的

`/origami:split-spec` で生成されたタスク一覧から、指定されたタスクID（TASK-XXX）の機能のみを処理します。既存の4コマンド（extract-features, generate-checklist, analyze-boundaries, generate-cases）を内部的に呼び出し、**機能別ディレクトリ（`F-XXX_{機能名}/`）**に結果を出力します。

**機能別ディレクトリ方式**: 各タスクは独立した機能ディレクトリに出力し、他機能のファイルは参照しません。これによりコンテキストの肥大化を防止します。

## 事前準備

1. **追加ルールの読み込み**
   - `docs/rule` ディレクトリが存在する場合は読み込み
   - `docs/rule/origami` ディレクトリが存在する場合は読み込み
   - 各ディレクトリ内のすべてのファイルを読み込み、追加ルールとして適用

2. **タスクファイルと出力先の確認** 🔵
   - task-list.md を検索（以下の順序で検索）:
     1. `docs/origami/*/tasks/task-list.md`（仕様書別ディレクトリ）
     2. `docs/origami/tasks/task-list.md`（レガシー形式、後方互換）
   - 存在しない場合はエラーメッセージを表示し、`/origami:split-spec` の実行を案内
   - **タスクテーブルから以下の情報を取得** 🔵:
     - 機能ID（F-XXX形式）
     - 機能名（日本語論理名）
     - 出力先（`docs/origami/{仕様書名}/F-XXX_{機能名}/` 形式）

3. **仕様書ルートディレクトリの検証** 🔵
   - task-list.mdから取得した仕様書ルートディレクトリの存在を確認
   - 存在しない場合はエラーメッセージを表示し、`/origami:split-spec` の再実行を案内

## 入力

| 引数 | 説明 | 必須 | 例 |
|------|------|------|-----|
| タスクID | 実行するタスクのID | ○ | `/origami:run-task TASK-001` |
| --phase | 実行するフェーズ（1-5）。省略時はPhase 1-4を順次実行 | - | `--phase 1` |

### フェーズ別実行マッピング 🔵

**信頼性**: 🔵 *PRD「フェーズ指定」表より*

| --phase | 実行コマンド | 入力 | 出力 |
|---------|-------------|------|------|
| 1 | extract-features | 仕様書 | `01_機能詳細.md` |
| 2 | generate-checklist | `01_機能詳細.md` | `02_動作仕様.md` |
| 3 | analyze-boundaries | `02_動作仕様.md` | `03_境界値分析.md` |
| 4 | generate-cases | `01` + `02` + `03` | `04_テストケース.md` |
| 5 | review-viewpoints | `04` + `01` + catalog | `05_観点レビュー.md` |

## 実行内容

**【信頼性レベル指示】**:
各項目について、入力仕様書との照合状況を以下の信号でコメントしてください：

- 🟢 **青信号**: 入力仕様書に明示的な記載がある
- 🟡 **黄信号**: テスト技法・業界標準・Web常識から推測
- 🔴 **赤信号**: 推測の根拠が薄い

### 0. --phase オプション判定 🔵

**信頼性**: 🔵 *PRD「実行内容（Option A）」より*

コマンド引数の `--phase` オプションを解析し、実行モードを決定します：

- **--phase 指定あり**: 単一フェーズ実行モード
- **--phase 省略**: 全フェーズ順次実行モード（後方互換）

### 1. 事前チェック

#### 1.1 タスク存在確認

- task-list.md から指定されたタスクIDを検索
- 該当タスクが見つからない場合はエラーメッセージを表示
- 見つかった場合は対象機能（F-XXX）を特定

#### 1.2 機能情報と出力先の取得 🔵
- task-list.mdの該当タスクセクションから以下を取得：
  - 機能ID（例: `F-001`）
  - 機能名（例: `ログイン`）
  - 出力先（例: `docs/origami/ecommerce-spec/F-001_ログイン/`）
- **出力先情報がない場合はエラー**:
  ```
  エラー: タスク {タスクID} に出力先情報が見つかりません。

  split-specコマンドを再実行してください:
  /origami:split-spec {仕様書パス}
  ```

#### 1.3 依存タスクチェック

- タスクの「依存タスク」フィールドを確認
- 依存タスクがある場合、そのチェックボックスの状態を確認
- 依存タスクが未完了の場合：

  ```text
  ⚠️ 警告: 依存タスクが未完了です

  未完了の依存タスク:
  - TASK-001: {機能名} (未完了)

  続行しますか？ (y/n)
  ```

- 依存タスクがすべて完了している場合、または依存タスクがない場合は処理を続行

#### 1.4 --phase指定時の前提チェック 🔵

**信頼性**: 🔵 *PRD「実行内容（Option A）」より*

`--phase` オプションが指定された場合、前フェーズの完了を確認します：

| --phase | 前提条件 |
|---------|---------|
| 1 | なし（仕様書が存在すること） |
| 2 | `01_機能詳細.md` が存在すること |
| 3 | `02_動作仕様.md` が存在すること |
| 4 | `01`, `02`, `03` が存在すること |
| 5 | `04_テストケース.md`, `01_機能詳細.md` が存在すること |

前提条件が満たされていない場合:

```text
エラー: Phase {N} を実行するには、先に Phase {N-1} を完了してください

未完了のフェーズ:
- Phase {N-1}: {必要なファイル名}

次のコマンド:
/origami:run-task {タスクID} --phase {N-1}
```

### 2. 機能ディレクトリの作成 🔵

**信頼性**: 🔵 *PRD「run-task変更点」より*

タスク実行開始時に、機能ディレクトリを作成します。

```
📁 機能ディレクトリを作成しています: F-XXX_{機能名}/
```

- 機能ディレクトリ（`F-XXX_{機能名}/`）が存在しない場合は作成
- 既に存在する場合はそのまま使用（上書きではなく更新）

### 3. 対象機能の処理

指定されたタスクIDに対応する機能（F-XXX）を処理します。
**各コマンドは機能ディレクトリを `--output` 引数で受け取ります** 🔵
**各フェーズは自機能フォルダ内のファイルのみを参照します（コンテキスト分離）** 🔵

#### 3.A --phase 指定時（単一フェーズ実行）🔵

**信頼性**: 🔵 *PRD「実行内容（Option A）」より*

指定されたフェーズのみを実行します。

| --phase | 実行コマンド | 入力 | 出力 |
|---------|-------------|------|------|
| 1 | `/origami:extract-features --output {機能ディレクトリ} --target F-XXX` | 仕様書 | `01_機能詳細.md` |
| 2 | `/origami:generate-checklist --output {機能ディレクトリ} --target F-XXX` | `01_機能詳細.md` | `02_動作仕様.md` |
| 3 | `/origami:analyze-boundaries --output {機能ディレクトリ} --target F-XXX` | `02_動作仕様.md` | `03_境界値分析.md` |
| 4 | `/origami:generate-cases --output {機能ディレクトリ} --target F-XXX` | `01` + `02` + `03` | `04_テストケース.md` |
| 5 | `/origami:review-viewpoints --output {機能ディレクトリ} --target F-XXX` | `04` + `01` + catalog | `05_観点レビュー.md` |

フェーズ完了後、task-list.md の該当フェーズのステータスを更新し、次のフェーズを案内します。

#### 3.B --phase 省略時（全フェーズ順次実行）🔵

**信頼性**: 🔵 *PRD「実行内容（Option A）」より*

Phase 1-4 を順次実行します（Phase 5 はオプションのため、明示的に `--phase 5` で実行）。各フェーズ完了後にユーザーへの確認プロンプトを表示します：

1. **Phase 1** (extract-features) を実行
   - 出力: `01_機能詳細.md`
   - task-list.md の Phase 1 を ✅ に更新
   - ユーザーに確認プロンプト「続行しますか？」

2. **Phase 2** (generate-checklist) を実行
   - 入力: `01_機能詳細.md` のみ（コンテキスト分離）
   - 出力: `02_動作仕様.md`
   - task-list.md の Phase 2 を ✅ に更新
   - ユーザーに確認プロンプト「続行しますか？」

3. **Phase 3** (analyze-boundaries) を実行
   - 入力: `02_動作仕様.md` のみ（コンテキスト分離）
   - 出力: `03_境界値分析.md`
   - task-list.md の Phase 3 を ✅ に更新
   - ユーザーに確認プロンプト「続行しますか？」

4. **Phase 4** (generate-cases) を実行
   - 入力: `01` + `02` + `03`（コンテキスト分離）
   - 出力: `04_テストケース.md`
   - task-list.md の Phase 4 を ✅ に更新
   - タスク全体を完了状態に更新

#### フェーズ別詳細

##### Phase 1: extract-features

- 対象機能の情報を `{機能ディレクトリ}/01_機能詳細.md` に出力
- コマンド: `/origami:extract-features --output {機能ディレクトリ} --target F-XXX`
- 入力: 仕様書（対象機能の該当部分のみ）
- **ファイル名**: `01_機能詳細.md`（単一機能形式）

##### Phase 2: generate-checklist

- 対象機能のMust/Never動作仕様を `{機能ディレクトリ}/02_動作仕様.md` に出力
- コマンド: `/origami:generate-checklist --output {機能ディレクトリ} --target F-XXX`
- 入力: `{機能ディレクトリ}/01_機能詳細.md` のみ（他機能のファイルは参照しない）
- 信号機システムを適用
- **ファイル名**: `02_動作仕様.md`（単一機能形式）

##### Phase 3: analyze-boundaries

- 対象機能の境界値分析表を `{機能ディレクトリ}/03_境界値分析.md` に出力
- コマンド: `/origami:analyze-boundaries --output {機能ディレクトリ} --target F-XXX`
- 入力: `{機能ディレクトリ}/02_動作仕様.md` のみ（他機能のファイルは参照しない）
- 信号機システムを適用
- **ファイル名**: `03_境界値分析.md`（単一機能形式）

##### Phase 4: generate-cases

- 対象機能のテストケースを `{機能ディレクトリ}/04_テストケース.md` に出力
- コマンド: `/origami:generate-cases --output {機能ディレクトリ} --target F-XXX`
- 入力: `{機能ディレクトリ}/01〜03` のみ（他機能のファイルは参照しない）
- TC-XXX-YY 形式でテストケースIDを付与
- 信号機システムを適用
- **ファイル名**: `04_テストケース.md`（単一機能形式）

##### Phase 5: review-viewpoints（オプション）🔵

- 対象機能のテスト観点レビューを `{機能ディレクトリ}/05_観点レビュー.md` に出力
- コマンド: `/origami:review-viewpoints --output {機能ディレクトリ} --target F-XXX`
- 入力: `{機能ディレクトリ}/04_テストケース.md` + `{機能ディレクトリ}/01_機能詳細.md` + プラグイン内蔵カタログ（他機能のファイルは参照しない）
- 信号機システム（レビュー用に適応）を適用
- STC-XXX-YY 形式で補完テストケース案IDを付与
- **ファイル名**: `05_観点レビュー.md`（単一機能形式）
- **注意**: `--phase` 省略時は実行されません。`--phase 5` で明示的に実行してください

### 4. タスク完了処理（フェーズ単位）🔵

**信頼性**: 🔵 *PRD「task-list.md フォーマット変更」より*

#### 4.1 フェーズ完了時の task-list.md 更新

各フェーズ完了時に、task-list.md の該当フェーズのステータスを更新します：

```markdown
## TASK-001: F-001 ログイン機能

| Phase | Status | Output |
|-------|--------|--------|
| 1 | ✅ | 01_機能詳細.md |
| 2 | ✅ | 02_動作仕様.md |
| 3 | 🔄 | - |
| 4 | ⏳ | - |
```

**ステータス凡例**:
- ⏳ 未着手
- 🔄 実行中
- ✅ 完了
- ⚠️ 要確認（🔴項目あり）

#### 4.2 全フェーズ完了時のタスク完了処理

4フェーズすべてが ✅ になった場合、タスク全体を完了状態としてマークします。

## 機能情報の解析方法 🔵

task-list.md の新フォーマット（フェーズ単位進捗管理形式）から機能情報と出力先を取得する方法:

### 新フォーマット（v3.1.0〜）

```markdown
## TASK-001: F-001 ログイン機能

**出力先**: docs/origami/ecommerce-spec/F-001_ログイン/

| Phase | Status | Output |
|-------|--------|--------|
| 1 | ✅ | 01_機能詳細.md |
| 2 | ✅ | 02_動作仕様.md |
| 3 | 🔄 | - |
| 4 | ⏳ | - |
```

**解析ルール**:

1. 指定されたタスクIDのセクション（`## TASK-XXX:`）を検索
2. セクションヘッダから以下を取得:
   - タスクID: `TASK-001`
   - 機能ID: `F-001`
   - 機能名: `ログイン機能`
3. 「**出力先**:」行から出力先パスを取得
4. フェーズテーブルから各フェーズのステータスを取得
5. 出力先パスの末尾に `/` がない場合は追加

### レガシーフォーマット（v3.0.x）

後方互換のため、従来形式も解析可能:

```markdown
### TASK-001: F-001 ログイン

| 項目 | 内容 |
|------|------|
| タスクID | TASK-001 |
| 機能ID | F-001 |
| 機能名 | ログイン |
| 出力先 | docs/origami/ecommerce-spec/F-001_ログイン/ |
| 依存タスク | なし |
| 状態 | 未完了 |
```

## 実行後の確認

### --phase 指定時

- 指定したフェーズの出力ファイルが作成されたことを確認
- task-list.md の該当フェーズのステータスが ✅ に更新されたことを確認
- 信号分布のサマリーを確認し、🔴項目がある場合は次のフェーズ実行前に修正を検討
- 出力ファイルをレビュー・修正してから次のフェーズを実行

### --phase 省略時（全フェーズ実行）

- 機能ディレクトリ（`F-XXX_{機能名}/`）が作成されたことを確認
- 各出力ファイル（`01_機能詳細.md`〜`04_テストケース.md`）が作成されたことを確認
- task-list.md の全フェーズのステータスが ✅ に更新されたことを確認
- 信号分布のサマリーを表示し、🔴項目がある場合は警告

## 機能別ディレクトリ方式について

### ディレクトリ構造

```text
    └── task-list.md
```

### コンテキスト分離 🔵

**信頼性**: 🔵 *PRD「提案方式」・REQ-101〜103より*

各フェーズは自機能フォルダ内のファイルのみを参照します：

| フェーズ | 入力 | 出力 |
|---------|------|------|
| Phase 1 (--phase 1) | 仕様書（対象機能部分のみ） | `01_機能詳細.md` |
| Phase 2 (--phase 2) | `01_機能詳細.md` のみ | `02_動作仕様.md` |
| Phase 3 (--phase 3) | `02_動作仕様.md` のみ | `03_境界値分析.md` |
| Phase 4 (--phase 4) | `01` + `02` + `03` | `04_テストケース.md` |
| Phase 5 (--phase 5) | `04` + `01` + catalog | `05_観点レビュー.md` |

**重要**: 他機能ディレクトリ（`F-002_ユーザー登録/`等）のファイルは参照しません。

**フェーズ別実行の利点**:
- 各フェーズ間でコンテキストがリセットされる
- 前フェーズの出力を確認・修正してから次フェーズを実行可能
- Phase 1 の推測ミスが後続フェーズに伝播することを防止

### メリット

1. **コンテキスト一定**: 各タスク実行時、自機能フォルダのみ参照
2. **独立性**: 機能単位で完結、並列レビュー可能
3. **再実行容易**: 特定機能だけ再生成可能
4. **可読性向上**: 機能論理名でディレクトリ内容が明確
