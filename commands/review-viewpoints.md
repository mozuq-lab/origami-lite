# review-viewpoints

## 目的

生成済みテストケースをテスト観点カタログ（TIS社テスト観点カタログv1.6 CC BY-SA 4.0ベース）と照合し、テスト観点の網羅性をレビューします。
信号機システムをレビュー用に適応して使用し、カバー済み観点・未カバー推奨観点・要確認観点を可視化します。未カバーの推奨観点に対しては補完テストケース案（STC形式）を自動生成し、テスト品質の向上を支援します。

**実行コンテキストに応じたファイル出力**:
- **単独実行時**: 複数機能を一覧形式で `05_観点レビュー一覧.md` に出力（後方互換）
- **タスク分割経由時**（`--target` 指定）: 単一機能の観点レビューを `05_観点レビュー.md` に出力

## 事前準備

1. **出力先ディレクトリの決定** 🔵
   - `--output` 引数が指定されている場合はそのディレクトリを使用
   - 指定がない場合は入力ファイル名から出力先を自動決定:
     - 入力ファイル名から拡張子を除去してディレクトリ名を生成
     - 出力先: `docs/origami/{仕様書名}/`
     - 例: `ecommerce-spec.md` → `docs/origami/ecommerce-spec/`

2. **前工程出力の確認**
   - `{出力先}/04_テストケース一覧.md` が存在する場合は読み込み（単独実行時）
   - `{出力先}/04_テストケース.md` が存在する場合は読み込み（タスク分割経由時）
   - `{出力先}/01_機能一覧.md` が存在する場合は読み込み（補助情報・単独実行時）
   - `{出力先}/01_機能詳細.md` が存在する場合は読み込み（補助情報・タスク分割経由時）
   - いずれも存在しない場合は、入力として指定された仕様書から直接処理

3. **追加ルールの読み込み**
   - `docs/rule` ディレクトリが存在する場合は読み込み
   - `docs/rule/origami` ディレクトリが存在する場合は読み込み
   - 各ディレクトリ内のすべてのファイルを読み込み、追加ルールとして適用

4. **出力ディレクトリの作成**
   - 出力ディレクトリが存在しない場合は作成

## 入力

### 引数 🔵

| 引数 | 説明 | 必須 | 例 |
|------|------|------|-----|
| 仕様書 | 入力ファイルまたはURL | △ | `docs/requirements.md` |
| --output | 出力先ディレクトリ（機能ディレクトリを含む） | △ | `--output docs/origami/my-spec/F-001_ログイン/` |
| --target | 対象機能ID（タスク分割経由時） | △ | `--target F-001` |
| --app-type | アプリ種別（カタログフィルタリング用） | - | `--app-type web` (default: web) |

**引数の組み合わせによる動作**:

| --target | --output | 出力ファイル名 | 用途 |
|----------|----------|---------------|------|
| なし | なし | `05_観点レビュー一覧.md` | 単独実行（全機能レビュー） |
| なし | あり | `05_観点レビュー一覧.md` | 単独実行（出力先指定） |
| あり | あり | `05_観点レビュー.md` | タスク分割経由（単一機能） |

**--app-type の指定値**:

| 値 | 説明 | 対象セクション |
|----|------|---------------|
| `web` | Webアプリケーション（デフォルト） | VAL + WEB + SEC-C + SEC-W + USA |
| `mobile` | モバイルアプリケーション | VAL + SEC-C + USA |
| `api` | REST API / バックエンドサービス | VAL + SEC-C |

### 入力優先度（単独実行時）

| 優先度 | 入力 | 説明 |
|--------|------|------|
| 1 | {出力先}/04_テストケース一覧.md + {出力先}/01_機能一覧.md + catalog | 前工程の出力（推奨） |
| 2 | {出力先}/04_テストケース一覧.md + catalog | テストケースのみから照合 |

### タスク分割経由時の入力制限 🔵

`--target` オプション指定時は、以下のルールに従います：

- **入力**:
  - `{出力先ディレクトリ}/04_テストケース.md`
  - `{出力先ディレクトリ}/01_機能詳細.md`
  - `origami-lite/data/viewpoint-catalog.md`（プラグイン内蔵カタログ）
- **重要**: 他の機能フォルダ（F-001_xxx/, F-002_xxx/ 等）のファイルは参照しない
- これにより、コンテキストサイズが一定に保たれます

### フェーズ間入力制限（v3.2.0） 🔵

**Phase 5（review-viewpoints）の入力制限**:

| 実行モード | 入力 | 備考 |
|-----------|------|------|
| タスク分割経由時 | `04_テストケース.md` + `01_機能詳細.md` + catalog | 仕様書・他機能フォルダは参照禁止 |
| 単独実行時 | `04_テストケース一覧.md` + `01_機能一覧.md` + catalog | 後方互換 |

- Phase 5は `04_テストケース.md` と `01_機能詳細.md` の2ファイルを参照（仕様書は参照しない）
- カタログはプラグイン内蔵データを使用（外部参照なし）
- 🔴項目がある場合は、テスト実行前にステークホルダー確認必須

タスク分割経由時（`--target` 指定時）:

   - `{機能ディレクトリ}/04_テストケース.md`

## 実行内容

1. **テストケースと機能詳細/機能一覧の読み込み**
   - 単独実行時: `04_テストケース一覧.md` と `01_機能一覧.md` を読み込み
   - タスク分割経由時: `04_テストケース.md` と `01_機能詳細.md` を読み込み
   - テストケースのGiven/When/Then、テストケース名、テストID（TC-XXX-YY）を抽出

2. **観点カタログの読み込み（アプリ種別でフィルタリング）**
   - `origami-lite/data/viewpoint-catalog.md`（プラグイン内蔵データ）を読み込み
   - `--app-type` に基づいて対象セクションをフィルタリング:
     - `web`: VAL + WEB + SEC-C + SEC-W + USA の全セクション
     - `mobile`: VAL + SEC-C + USA
     - `api`: VAL + SEC-C
   - 各観点のID（VP-XXX-NNN）、観点名、キーワード、対象を抽出
   - アプリ種別に合致しないセクションは「対象外」としてスキップ（カウントに含めない）

3. **各観点をテストケースと照合（キーワードマッチング + セマンティックマッチング）**
   - カタログの各観点のキーワードをテストケースのGiven/When/Then、テストケース名と照合
   - キーワード一致: 観点のキーワードがテストケースの記述に含まれるか
   - セマンティック一致: 観点の意図とテストケースの目的が意味的に合致するか
   - 機能ごとに照合スコープを絞り込み（F-001の観点はF-001のテストケースと照合）

4. **カバレッジ分類**
   - 🟢 カバー済: 対応するテストケースが存在（対応するTC-XXX-YY を記録）
   - 🟡 未カバー推奨: 未カバーだが対象機能に該当しそう → 補完テストケース案を生成
   - 🔴 要確認: 未カバーで該当性が不明 → ステークホルダーに確認
   - 対象外: アプリ種別やドメインに合致しない → スキップ（カウントに含めない）

5. **🟡項目に対して補完テストケース案を生成**
   - STC-XXX-YY 形式のIDを付与（STC = Supplementary Test Case）
   - XXX: 機能番号（F-001 → 001）、YY: 連番
   - Given/When/Then形式で具体的な補完テストケースを生成
   - 対応する観点ID（VP-XXX-NNN）を根拠として明記

6. **カバレッジサマリー・信号分布の集計**
   - セクション別（VAL / WEB / SEC-C / SEC-W / USA）のカバレッジを算出
   - カバー率 = 🟢件数 / 対象観点数 × 100%
   - 全体のカバレッジサマリーを生成

7. **出力ファイル名の決定** 🔵

   実行コンテキストに応じて出力ファイル名を切り替え：

   ```text
   IF --target オプションが指定されている THEN
     出力ファイル名 = "05_観点レビュー.md"
   ELSE
     出力ファイル名 = "05_観点レビュー一覧.md"
   END IF
   ```

   | 条件 | 出力ファイル名 | 出力形式 |
   |------|---------------|---------|
   | 単独実行（--targetなし） | `05_観点レビュー一覧.md` | 複数機能を一覧形式で記載 |
   | タスク分割経由（--targetあり） | `05_観点レビュー.md` | 単一機能の観点レビューを記載 |

## 信号機判定基準

本コマンドでは信号機システムをレビュー用に適応して使用します：

| 信号 | 判定条件 | 例 |
|------|---------|-----|
| 🟢 カバー済 | 既存テストケースで観点がカバーされている | TC-001-03がVP-VAL-001に対応（バリデーションの正常系が存在する） |
| 🟡 未カバー推奨 | 未カバーだが対象機能に該当すると推測される | フォームを持つ機能なのにバリデーション観点がカバーされていない |
| 🔴 要確認 | 未カバーで該当性が不明 | ドメイン固有の観点で機能への適用可否が不明 |

**判定の考え方**:
- 🟡の「該当すると推測」: テスト観点の意図と機能の性質が業界標準の観点から合致する場合
- 🔴の「該当性が不明」: 機能詳細のみでは適用可否を判断できない場合（確認なしに判断不可）
- 対象外: アプリ種別のフィルタリングで除外された観点（例: webでなければWEBセクションは対象外）

## 観点レビューの参考

### 観点カタログのセクション構成

本コマンドが参照するテスト観点カタログ v1.6 のブラックボックステスト関連セクション：

| セクションID | セクション名 | 主な観点の例 |
|------------|------------|------------|
| VAL | バリデーション | 入力値の形式・範囲・必須チェック、文字種・文字数制限 |
| WEB | ウェブアプリケーション | ページ遷移、ブラウザ互換性、レスポンシブ対応、セッション管理 |
| SEC-C | セキュリティ共通 | 認証・認可、データ保護、ログ・監査、エラー処理 |
| SEC-W | セキュリティウェブ | XSS、SQLインジェクション、CSRF、クリックジャッキング |
| USA | ユーザビリティ | アクセシビリティ、操作性、エラーメッセージ、フィードバック |

### カバレッジ目標の考え方

カバー率の目標値は、プロジェクトのリスク許容度によって調整してください：

| カバー率 | リスクレベル | 適用場面 |
|---------|------------|---------|
| 80%以上 | 低（高品質要求） | 金融・医療・セキュリティ重視のサービス |
| 70%以上 | 中（標準） | 一般的なWebアプリケーション（推奨） |
| 50%以上 | 高（最低限） | MVP・プロトタイプ・内部ツール |

### 補完テストケース案の活用方法

🟡項目に対して生成される補完テストケース案（STC-XXX-YY）は、以下の方法で活用できます：

1. **そのまま追記**: `04_テストケース.md` に補完テストケース案をコピーして追記し、テスト実行の対象に含める
2. **動作仕様に追加して再生成**: `02_動作仕様.md` に対応するMust/Never項目を追加した上で、`/origami:generate-cases` を再実行することで、整合性の取れたテストケースを生成する
3. **対象外として記録**: チームの判断で特定の観点を対象外とする場合は、その理由を `05_観点レビュー.md` に記録する

### 照合精度に関する注意事項

キーワードマッチングとセマンティックマッチングを組み合わせていますが、以下の点に注意してください：

- 🟢として分類された観点でも、テストケースの深度（正常系のみでエラー系なし等）は別途確認を推奨
- 🟡として分類された観点の「補完テストケース案」は生成時点のAI推論であるため、ドメイン専門家によるレビューが必要
- 🔴として分類された観点は、機能仕様の文脈なしに適用可否を判断できないため、必ずステークホルダーに確認

## v3.2.0 Breaking Change

### Phase 5 の追加とフェーズ間入力制限の拡張

**v3.2.0** で Phase 5（review-viewpoints）が追加されました。フェーズ間入力制限が全5フェーズに拡張されています：

| フェーズ | コマンド | 入力 | コンテキストサイズ |
|---------|---------|------|-----------------|
| Phase 1 | extract-features | 仕様書（対象機能部分） | 仕様書に依存 |
| Phase 2 | generate-checklist | `01_機能詳細.md` のみ | 一定 |
| Phase 3 | analyze-boundaries | `02_動作仕様.md` のみ | 一定 |
| Phase 4 | generate-cases | `01` + `02` + `03` の3ファイル | 一定（3ファイル分） |
| **Phase 5** | **review-viewpoints** | **`04` + `01` + catalog** | **一定（2ファイル + catalog分）** |

**Phase 5 はオプションです**:
- Phase 4（generate-cases）でテストドキュメント生成は完結します
- Phase 5 は観点網羅性の向上を目的としたオプションのレビューステップです
- 既存の Phase 1〜4 ワークフローへの影響はありません（後方互換）
- `run-task` コマンドで `--phase 5` を指定することで、タスク分割フローに組み込むことができます

**移行時の注意**:
- Phase 5 は仕様書を直接参照しません
- `origami-lite/data/viewpoint-catalog.md` がプラグインに内蔵されている必要があります
- 単独実行モード（`--target` なし）の動作は Phase 4 以前と同じ考え方を踏襲しています
